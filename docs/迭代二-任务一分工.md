## 一、项目定位与实验要求对齐

| 课程要求 | 本框架对策 |
|----------|------------|
| Agent 展现规划与思考，非简单预定义 workflow | **自治 Agent**（`IAutonomousAgent`）：**运行时**由 LLM 产出/修订 `ExecutionPlan` 与工具决策；仓库中 `StubPlanGenerator` 仅为占位，正式实现需替换为 **LLM 规划器** |
| ≥2 个主题相关外部工具 | 三套工具契约：`weather_forecast`、`maps_route_estimate`、`calendar_conflict_check`；**`stubTools.ts` 仅占位**，成员3 替换为真实 API |
| 自我修正与异常处理 | **ReflexionPolicy**（`IReflexionPolicy`）：工具失败后可 `retry` / `skip` / `abort`；可升级为 LLM 诊断 |
| 内部状态流转可视化 | **ReasoningEvent** 流 + `/demo` 页 **TracePanel**；可选 Convex 持久化（见下文） |
| 加分：多种推理框架结合 | **Plan-and-Execute**（外层）+ **ReAct**（内层单步）+ **Reflexion**（失败反思）——答辩时说明三者分工与数据流 |
| API Key 不硬编码 | 仅允许 `process.env.*` / Convex 环境变量；`.env.example` 已列键名 |

## 三、接口规范（完整定义）

以下类型均在 **`lib/agent/contracts.ts`** 中以 TypeScript 声明，此处为语义说明与协作契约。

### 3.1 领域与输入

| 名称 | 说明 |
|------|------|
| `UserGoal` | `rawText` + 可选 `slots`（出发地、目的地、日期、预算、节奏等） |
| `BusyWindow` | 用户忙碌区间 `start`/`end`（unix ms）+ 可选 `label` |
| `UserContext` | `userId`、`preferences`（`TripPreferences`）、可选 `calendarBusyWindows` |
| `AgentRunInput` | `sessionId` + `goal` + `context` |

### 3.2 规划（Plan-and-Execute）

| 名称 | 说明 |
|------|------|
| `ExecutionPlan` | `planId` + `phases[]` |
| `PlanPhase` | `id`、`title`、`steps[]` |
| `PlanStep` | `id`、`description`、可选 `suggestedTools[]`（`ToolName`） |
| `IPlanGenerator` | `draftPlan(input) → ExecutionPlan`；`revisePlan(plan, feedback) → ExecutionPlan` |
| `IAutonomousAgent` | 继承 `IAgentOrchestrator`；**自治语义**：计划与单步工具决策由 **LLM 在运行时**生成；`StubPlanGenerator` 仅占位，正式实现须替换 |

### 3.3 工具层

| 名称 | 说明 |
|------|------|
| `ToolName` | 仅允许：`weather_forecast` \| `maps_route_estimate` \| `calendar_conflict_check` |
| `ToolContext` | `userId`、`stepId`、`userContext` |
| `ToolResult<T>` | `ok: true` + `data` **或** `ok: false` + `error: ToolError` |
| `ToolError` | `code`、`message`、`retryable`、`cause?` |
| `ToolDefinition<TArgs,TData>` | `name`、`description`、`argsSchema`（Zod）、`execute(args, ctx)` |
| `IToolRegistry` | `list()`、`get(name)` |

**各工具参数（实现须通过对应 Zod schema）**

1. **weather_forecast**：`{ city: string; dateIso?: string }`  
2. **maps_route_estimate**：`{ origin: string; destination: string; mode: 'transit'|'driving'|'walking' }`  
3. **calendar_conflict_check**：`{ proposedStart: number; proposedEnd: number; label?: string }`  
   - 与 `UserContext.calendarBusyWindows` 做区间重叠检测。

### 3.4 ReAct 与编排

| 名称 | 说明 |
|------|------|
| `ReactTurn` | `turnIndex`、`thought`、`toolName`、`toolArguments`、`toolResultSummary` |
| `IReactExecutor` | `executeStep({ sessionId, emitter, plan, step, context, goal }) → AsyncIterable<ReasoningEvent>` |
| `IEventEmitter` | `emit(partial) → ReasoningEvent`（由 `SessionEmitter` 实现） |
| `IAgentOrchestrator` | `run(input) → AsyncIterable<ReasoningEvent>` |

### 3.5 可视化事件 `ReasoningEvent`

| `type` | `payload` 要点 |
|--------|----------------|
| `session_start` | `{ goal: string }` |
| `plan_draft` / `plan_final` | `{ plan: ExecutionPlan }` |
| `react_thought` | `ReactTurn` |
| `tool_call` | `{ stepId, toolName, args }` |
| `tool_result` | `{ stepId, toolName, summary }` |
| `tool_error` | `{ stepId, toolName, error: ToolError }` |
| `reflexion` | `{ stepId, diagnosis, nextAction: 'retry'\|'skip'\|'abort' }` |
| `step_done` | `{ stepId }` |
| `run_done` | `{ summary }` |
| `run_error` | `{ message }` |

### 3.6 LLM

| 名称 | 说明 |
|------|------|
| `ILLMClient` | `complete(messages)`；可选 `completeWithTools(messages, tools)` |
| `ChatMessage` | `role`: `system`\|`user`\|`assistant` |

### 3.7 轨迹持久化（可选，Convex）

**表**（见 `convex/schema.ts`）：

- `agentSessions`：`userId`、`status`、`goalText`、`createdAt`
- `agentTraceEvents`：`sessionId`、`seq`、`type`、`payloadJson`、`ts`；索引 `by_session_seq`

**待实现函数契约（成员5 在 `npx convex dev` 生成 `_generated` 后新增 `convex/trace.ts`）**

| 函数 | 类型 | 参数 | 行为 |
|------|------|------|------|
| `appendEvent` | `mutation` | `sessionId, seq, type, payloadJson, ts` | 插入一条事件 |
| `listEventsBySession` | `query` | `sessionId` | 按 `seq` 升序返回事件列表 |

`ITraceSink`：`emit(event: ReasoningEvent) → Promise<void>`；`ConvexTraceSink` 将 `event` 序列化为 JSON 字符串写入 `payloadJson`。

### 3.8 HTTP API（当前）

| 方法 | 路径 | 请求体 | 响应 |
|------|------|--------|------|
| `POST` | `/api/agent/run` | 见 `app/api/agent/run/route.ts` 内 `bodySchema`（与 `AgentRunInput` 对齐） | `{ events: ReasoningEvent[] }` |

## 四、六人分工（任务一）

本部分从**总体目标**与**代码实现**两条线说明：项目定位为 **自治 Agent**（`IAutonomousAgent`），即 **规划与工具调用由 LLM 在运行时决定**；仓库当前仅为**接口 + 占位实现**，各成员在**不破坏 `contracts.ts` 已公开类型**的前提下填充实现。

**数据流一句话（便于理解分工）**：用户请求 → `app/api/agent/run/route.ts` → `createAutonomousAgentPipeline()` → `PlanExecuteOrchestrator.run` 先问 **`IPlanGenerator` 要计划**，再对每一步调用 **`IReactExecutor.executeStep`**（内部用 `IToolRegistry` 调工具、用 **`IReflexionPolicy`** 处理失败）→ 全程通过 **`SessionEmitter`** 产出 **`ReasoningEvent`** 给前端或 Convex。

---

### 成员1 — 自治 Agent 编排与运行时集成负责人

**总体职责（通俗理解）**

- 把整件事想成「**导演**」：用户说一句话，系统要**先出计划、再一步步执行**；成员1 保证这两段**顺序不乱、接口不断、别人换演员（换 LLM、换工具）时戏还能演下去**。
- 不负责「模型怎么写 Prompt」（那是成员2），**负责**「**什么时候**出计划、**什么时候**改计划、**什么时候**算跑完」以及「**怎么把所有人写的模块拼成一个可运行的 `pipeline.run()`**」。

**在项目代码中的位置与作用**

- 占据 **编排层**：`lib/agent/orchestrator/PlanExecuteOrchestrator.ts` 是 **`IAutonomousAgent` 的默认实现**，内部串联 `IPlanGenerator` → 遍历步骤 → `IReactExecutor`；`lib/agent/orchestrator/factory.ts` 的 **`createAutonomousAgentPipeline`** 是「**组装入口**」，其他成员替换实现时通常在这里改**注入**。
- 占据 **HTTP 边界**：`app/api/agent/run/route.ts` 是浏览器/外部调用 Agent 的入口，负责把 JSON 转成 `AgentRunInput` 并调用 pipeline。
- 与 **事件顺序**强相关：`lib/agent/runtime/SessionEmitter.ts` 的 `seq` 全局递增，**编排器不应再套一层序号**，否则 Trace 会乱。

**代码实现要点（对应文件）**

| 文件路径 | 成员1 要做的事 |
|----------|----------------|
| `lib/agent/orchestrator/PlanExecuteOrchestrator.ts` | 明确何时调用 `revisePlan`（当前为占位字符串）；正式版应传入用户追加约束、工具失败摘要、LLM 反思等；必要时在 `run` 内对 `run_error` 做统一收尾。 |
| `lib/agent/orchestrator/factory.ts` | 将 `StubPlanGenerator` / `ReflexionPolicy` / `ReactExecutor` 的依赖替换为成员2/4 的实现时，**保持构造函数与 `createAutonomousAgentPipeline` 导出稳定**；可新增 `createLLMPipeline()` 等别名但需文档化。 |
| `app/api/agent/run/route.ts` | 维护请求体校验（`bodySchema`）；可改为 **SSE** 或流式返回 `ReasoningEvent`，与成员5 约定协议；长任务超时与错误 JSON 格式。 |
| `lib/agent/runtime/SessionEmitter.ts` | 一般不改逻辑；若新增事件类型，需与 `lib/agent/contracts.ts` 同步，并告知成员5。 |
| `lib/agent/contracts.ts` | 若需扩展编排相关类型（如 `revisePlan` 的 feedback 结构），**发起 MR 并拉成员6 评审文档** |

**联调与验收**

- 与成员2：确认 `draftPlan` / `executeStep` 内 LLM 失败时是否中断 `run`、是否 `emit('run_error')`。
- 与成员4：确认 `reflexion` 后是否 `revisePlan`、是否 `step_done`。
- **验收**：更换实现后，`POST /api/agent/run` 仍能返回完整事件链；`contracts.ts` 无破坏性变更或已走团队评审。

### 成员2 — LLM 层与「自治推理」核心（规划 + ReAct 工具决策）

**总体职责（通俗理解）**

- 把 Agent 想成一个人：**先想清楚「分几步做」**，再**每一步想「该查天气还是查地图」、参数怎么填**——成员2 就是 **大脑**：让 **LLM 真的参与决策**，而不是写死「第一步永远查天气」。
- 当前仓库里 **`StubPlanGenerator`** 和 **`ReactExecutor` 里的占位 `stubToolArgs`** 都是「假大脑」，**正式版要换成会调模型、会解析 JSON 的版本**。

**在项目代码中的位置与作用**

- 对接 **`lib/agent/contracts.ts` 里的 `ILLMClient`**：所有「问模型」的代码应集中通过 **`lib/agent/llm/OpenAICompatibleClient.ts`**（或 `MockLLMClient.ts` 降级），避免在页面或工具里散落 `fetch` 调大模型。
- **规划**侧：实现新的 **`IPlanGenerator`**（建议新文件 `lib/agent/plan/LLMPlanGenerator.ts`），**替换** `factory.ts` 里对 `StubPlanGenerator` 的引用。
- **执行**侧：改 **`lib/agent/loops/ReactExecutor.ts`**，在单步内用 `completeWithTools` 产出 `thought`、工具名、参数，替代文件内的 **`stubToolArgs` 函数**。

**代码实现要点（对应文件）**

| 文件路径 | 成员2 要做的事 |
|----------|----------------|
| `lib/agent/contracts.ts` | 若需扩展 `ILLMClient`（如流式、新参数），在团队评审后修改；同步成员6。 |
| `lib/agent/llm/OpenAICompatibleClient.ts` | 实现 `complete` 与 `completeWithTools`；从 `process.env` 读 `DASHSCOPE_*`；解析 `tool_calls`、与 Zod 校验失败时的错误信息。 |
| `lib/agent/llm/MockLLMClient.ts` | 无密钥时降级策略：固定返回或抛错，与成员1 约定是否 `run_error`。 |

- **验收**：`plan_draft` / `plan_final` 随用户输入变化；`react_thought` 为自然语言而非固定模板。

### 成员3 — 外部工具与真实世界交互（主题相关 ≥2）

**总体职责（通俗理解）**

- Agent **不能只会聊天**：要「**真的去查天气、算路程、对日程**」——成员3 就是 **手和传感器**：**把网上的 API 变成代码里可调用的函数**，并把失败变成「**可重试**还是**没救了**」，让上面的 Reflexion 知道怎么办。

### 成员4 — Reflexion 策略与异常自修正

**总体职责（通俗理解）**

- 工具会挂、网络会抖——**出错了不能装死**：要 **说清楚哪错了**、**要不要重试**、**还是跳过这一步**——成员4 管的就是 **「摔倒了怎么爬起来」**。
- 课程里的 **自我修正** 主要落在这：**`reflexion` 事件** 在页面上要看得见。

**在项目代码中的位置与作用**

- 可选新文件 **`lib/agent/reflexion/LLMReflexionPolicy.ts`**，在 **`factory.ts`** 中替换注入。

**代码实现要点（对应文件）**

**联调与验收**
